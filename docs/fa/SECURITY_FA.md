## ۱. احراز هویت

- **کوکی نشست.** ورود، اعتبارنامه را با یک توکن تصادفی ۲۵۶بیتی op exchange می‌کند که در کوکی `dh_session` می‌نشیند — `httpOnly`، `SameSite=Lax`، مسیر `/`، عمر ۲۴ ساعت. نشست‌ها سمت سرور در جدول `Session` نگه داشته می‌شوند؛ logout آن‌ها را حذف می‌کند (آزمایش‌شده: درخواست با کوکی قدیمی بعد از logout → 401).
- **هش رمز عبور.** PBKDF2-SHA256 با ۶۰هزار تکرار، کلید ۳۲بایتی و salt تصادفی ۱۶بایتی؛ ذخیره به شکل `pbkdf2$<salt>$<hash>`.
- **نقش‌ها سمت سرور اعمال می‌شوند.** هر route قبل از انجام کار، نشست و نقش را resolve می‌کند. UI کلاینت اکشن‌های غیرمجاز را مخفی می‌کند، ولی مخفی‌سازی آرایشی است — اعمال واقعی سمت سرور است (با فراخوانی مستقیم API به‌عنوان VIEWER آزمایش شد: 403 + ثبت در audit).
- **انقضا.** نشست منقضی در اولین استفاده رد و حذف می‌شود.

حساب‌های دموی seed: `admin/admin123`، `operator/operator123`، `viewer/viewer123` — فقط برای توسعه.

## ۲. نقش‌ها

| قابلیت | ADMIN | OPERATOR | VIEWER |
|---|---|---|---|
| خواندن APIها / همه نماها | ✔ | ✔ | ✔ |
| ارسال فرمان | ✔ | ✔ | ✘ (403 + audit) |
| مدیریت قواعد (CRUD + نسخه‌بندی) | ✔ | ✔ | ✘ |
| پذیرش/رفع هشدار | ✔ | ✔ | ✘ |
| کنترل شبیه‌ساز و گیت‌وی | ✔ | ✘ | ✘ |
| مدیریت کاربران | ✔ | ✘ | ✘ |

رد شدن نقش‌ها (`ROLE_DENIAL` با outcome `DENIED`) در audit ثبت می‌شوند — ثبت audit هرگز اجرای سیاست را بلاک نمی‌کند.

## ۳. مرز API داخلی

Routeهای زیر `/api/internal/*` (ingest و export تله‌متری، وضعیت دستگاه، status/رخداد گیت‌وی، هشدار، قواعد، اجرای قواعد، وضعیت فرمان، ناهنجاری، analytics-run) **نشست نمی‌پذیرند** — فقط هدر `X-Internal-Token`:

- گیت‌وی، شبیه‌ساز و سرویس تحلیل با همین توکن صحبت می‌کنند؛
- پیکربندی با `DH_INTERNAL_TOKEN`؛ مقدار پیش‌فرض `dev-internal-token` **فقط برای توسعه** است؛
- نبود/خطای توکن → 401 (آزمایش‌شده).

endpoint ارسال رخداد realtime (`POST /emit` روی ۳۰۱۳) همان توکن را می‌خواهد و به‌علاوه نام رخداد باید در allow-list سروری باشد؛ رخداد ناشناخته → 400.

## ۴. پوشش audit

هر رکورد `AuditEvent` شامل actor (USER / GATEWAY / SYSTEM / DEVICE / AI)، action، resource، outcome (SUCCESS / FAILURE / DENIED) و جزئیات سازگارشده. ثبت می‌شود:

- ورود و خروج؛
- رد شدن نقش و رد شدن فرمان خارج از قابلیت‌های دستگاه (با دلیل)؛
- گذارهای چرخه حیات فرمان؛
- به‌روزرسانی قواعد (با نسخه)؛
- پذیرش و رفع هشدار؛
- رخدادهای گیت‌وی (CONNECTED / BUFFERING / DRAINING / DRAINED / OVERFLOW)؛
- استفاده از AI (درخواست‌ها و پیشنهادها).

اسکن secret در مجموعه تست امنیت بررسی می‌کند که credential در سورس و لاگ‌ها نباشد.

## ۵. مرز ایمنی AI

در کد مسیر API اعمال می‌شود، نه با تکیه بر مدل:

1. مدل فقط evidence سازگارشده می‌بیند (خلاصه‌ها، هشدارها، یافته‌ها، فراداده قواعد، آمار تله‌متری) — بدون credential و توکن.
2. **اجرا نمی‌تواند فرمان بدهد.** خواستنِ اجرا → رد + پیشنهاد فرمان برای اپراتور مجاز از مسیر ممیزی‌شده. آزمایش واقعی: بعد از خواستن صریح اجرا، شمار فرمان‌های با منشأ AI در audit **صفر** ماند.
3. خروجی باید گزاره‌ها را برچسب‌گذاری کند (`[measured fact]` / `[rule result]` / `[ML output]` / `[hypothesis]` / `[recommendation]`) و score ناهنجاری همیشه به‌عنوان score غیرکالیبره معرفی شود.
4. ورودی محدود (سقف سؤال و evidence) و پلتفرم بدون AI هم کاملاً کار می‌کند.

جزئیات بیشتر: [LOCAL_AI_FA.md](LOCAL_AI_FA.md).

## ۶. اعتبارسنجی ورودی

- envelope تله‌متری: اعتبارسنجی کامل پروتکل v1 در گیت‌وی (نسخه، شناسه، تطابق تاپیک، انحراف زمانی، whitelist متریک، enum کیفیت، سقف اندازه) — [DEVICE_PROTOCOL_FA.md](DEVICE_PROTOCOL_FA.md).
- فرمان: اکشن با **قابلیت‌های دستگاه** چک می‌شود؛ payload به‌ازای اکشن اعتبارسنجی می‌شود (مثلاً `SET_INTERVAL` نیاز به `intervalSec` در [۲، ۳۰۰] دارد)؛ رد شدن‌ها audited.
- batch: حداکثر ۵۰۰ پیام در هر فراخوانی ingest → 413؛ سقف ۶۴KiB هر پیام MQTT در گیت‌وی؛ سقف ۲MB بدنه emit در realtime.
- شناسه دستگاه با regex `^DH-[A-Z0-9-]+$` در ingest، dispatch فرمان و اشتراک اتاق realtime کنترل می‌شود.

## ۷. محدودیت‌های شناخته‌شده — الزامات محیط عملیاتی

| محدودیت این ساخت | الزام عملیاتی |
|---|---|
| broker MQTT روی TCP خام ۱۸۸۳، کلاینت بی‌نام، بدون TLS | listener با TLS (مثلاً ۸۸۸۳) + گواهی سرور؛ گواهی کلاینت به‌ازای دستگاه/گیت‌وی؛ credential و ACL هر کلاینت |
| توکن داخلی مشترک توسعه (`dev-internal-token`) | credential یکتا به‌ازای هر سرویس، چرخشی، با secret manager |
| رمزهای دمو در مخزن seed شده | تدارک credential واقعی + سیاست رمز عبور |
| SQLite با فایل محلی | PostgreSQL (یا معادل) با کنترل دسترسی، backup و رمزنگاری در حال سکون |
| بدون HTTPS درون‌اپ (پروکسی توسعه Caddy در سندباکس) | TLS لبه، HSTS، پرچم‌های امن کوکی |
| CORS سرویس realtime با `origin: *` | محدودکردن به origin وب |
| بدون rate limit (به‌جز سقف اندازه) | محدودیت نرخ روی endpointهای عمومی |
| مدیریت نشست فقط با logout | سیاست نشست (تایم‌اوت بی‌کاری، ابطال اجباری) |

هیچ‌کدام از این‌ها در تست‌ها پنهان نشده — مجموعه امنیت همان‌هایی را که سیستم واقعاً اعمال می‌کند (authn/authz، مرز توکن، audit، اعتبارسنجی، ایمنی AI) آزمایش می‌کند و ۳۷/۳۷ سبز شده است.

`bash tests/security.test.sh` (نیازمند پلتفرم در حال اجرا):

| گروه | چه چیزی می‌سنجد | مکانیزم تأییدشده |
|---|---|---|
| S1 دسترسی بدون احراز هویت | API بدون نشست | 401 روی routeهای محافظت‌شده |
| S2 اعمال نقش | مرزهای VIEWER/OPERATOR/ADMIN برای هر قابلیت | 403 در موارد لازم، مجاز در بقیه |
